## Why

Chronicle's release publication today depends on GitHub's auto-generated notes (`gh release create --generate-notes`), which dump raw commit history into the release body and say nothing about what a Chronicle user can actually do. The workflow also assumes the ambient `GITHUB_TOKEN` for every `gh` invocation, never checks that the pushed tag matches the workspace version before building, and can mark a release run complete while the required `SHA256SUMS` asset is missing from the release. This change hardens publication: release notes are generated by the Pi coding agent from a repository-managed prompt (via `shaftoe/pi-coding-agent-action`, an OpenCode Go custom provider, and the OpenAI-compatible Chat Completions API), tag/version consistency is enforced before any build, `gh` gains explicit authentication and repository context, checksum completion is asserted, and the workflow is covered by portable static tests.

## What Changes

- Add `.github/prompts/release-notes.md`: a repository-managed external prompt (Markdown-only, no GitHub Actions expressions) that instructs the agent to inspect the checked-out repository and git history itself — current tag, previous semantic-version tag (or initial public release), shipped vs planned functionality, user-facing focus, and the exact release-note structure (`## Highlights`, `## Installation`, `## What's included`, `## Known limitations`).
- Add a `release-notes` job to `.github/workflows/release.yml`: checks out with full history (`fetch-depth: 0`), writes the OpenCode Go custom provider into `~/.pi/agent/models.json` (env-driven `baseUrl`, `api`, `authHeader`, model id; `apiKey` references the `OPENCODE_GO_API_KEY` environment-variable name, never the secret value), loads the prompt file, invokes the pinned immutable `shaftoe/pi-coding-agent-action@v2.27.0` with the model/thinking-level from workflow env, saves `steps.*.outputs.response` to `release-notes.md`, and uploads it as an artifact. The job fails closed: any Pi/OpenCode Go failure stops the pipeline — no fallback to `--generate-notes`.
- Publish: `publish` now depends on both the binary build matrix and `release-notes`; it downloads the release-notes artifact and creates the release with `--notes-file release-notes.md --verify-tag`, removing `--generate-notes`.
- Add an early `validate-tag` job (scripts/release/validate-tag.sh) that fails before any build when the pushed tag does not match the root `Cargo.toml` workspace version (derived, never hardcoded).
- Fix `gh` execution context: every job that invokes `gh` declares `GH_TOKEN` and `GH_REPO` explicitly; only `publish`/checksum jobs hold `contents: write`, the rest stay read-only.
- Checksums: the post-publish checksum job (compose one deterministic `SHA256SUMS` over all target archives, `sha256sum -c` verify, `gh release upload --clobber`) is preserved and gains an explicit assertion that the release carries the expected `SHA256SUMS` asset, so a release is not considered successfully completed without it.
- Add portable static/behavioral tests (`scripts/tests/validation/test_release_workflow.py`) protecting: prompt file existence, prompt not inlined in the workflow, no `--generate-notes`, publication consumes `release-notes.md`, `gh` auth/repo context, tag/workspace-version mismatch failure, and env-driven OpenCode Go provider configuration; wire them into `scripts/validate.sh` and the test catalog.

## Capabilities

### Modified Capabilities

- `release-packaging`: the release publication contract gains Pi-generated release notes as the authoritative release body, early tag/workspace-version validation, explicit `gh` authentication/repository context with least-privileged permissions, and checksum-completion assertion (release not complete without the `SHA256SUMS` artifact).
- `layered-validation`: release-workflow static/behavioral tests join the portable validation layer (`tooling:validation-tests`), so workflow regressions are caught without privileged gates.

## Impact

Affected code: new `.github/prompts/release-notes.md`, `scripts/release/validate-tag.sh`, `scripts/release/write-opencode-go-models-json.py`; modified `.github/workflows/release.yml`.

Affected non-code: `scripts/validate.sh` and `validation/test-architecture/test-catalog.toml` (new release-workflow test wiring), new `scripts/tests/validation/test_release_workflow.py`.

No changes to WAL, ETL, canonical session, storage, replay, capture, eBPF, recorder, or CLI product behavior. No new LLM SDK, no custom OpenCode Go client, no release tag created or pushed by this change, and no GitHub Release published by this change. Secrets stay out of the repository: the API key is supplied exclusively via the `OPENCODE_GO_API_KEY` Actions secret.

- Add a manual `workflow_dispatch` dry-run trigger that executes the real release preparation path (context resolution, eBPF/CLI builds, per-target packaging, Pi release notes, archive collection, `SHA256SUMS` generation and verification, prepared-bundle upload, run summary) and never publishes: publication and all release-mutating `gh` commands are gated to `github.event_name == 'push'` plus `startsWith(github.ref, 'refs/tags/v')`. Dry-run version/tag context comes from the root `Cargo.toml` via a single testable script (`scripts/release/resolve-release-context.sh`, superseding `validate-tag.sh`), and checksum generation/verification move before publication into a shared `prepare-release` job.
