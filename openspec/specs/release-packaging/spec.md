## Purpose

Minimal release packaging so a public developer-facing installation path is real: a GitHub Actions release workflow that produces supported Linux binaries with the eBPF capture object embedded, versioned archives, SHA-256 checksums, GitHub Release artifacts, and `chronicle --version` reporting. Distribution channels beyond raw release artifacts (package managers, Docker, Homebrew, crates.io) are explicit non-goals.

## Requirements

### Requirement: Release workflow and targets

The repository SHALL provide a release workflow triggered on version tags that builds release binaries for supported targets: x86_64 Linux and aarch64 Linux on native runners. Each release binary SHALL be built with `--locked` on the Linux target so live eBPF capture is available in the shipped artifact automatically (selected from the compilation target; no feature flag), with the eBPF object built from `ebpf/` source (nightly + rust-src + bpf-linker, `-Z build-std=core`, `--target bpfel-unknown-none --release`) and embedded through the existing `chronicle-capture-ebpf` build path.

#### Scenario: Tagged release builds

- **WHEN** a `v*` tag is pushed
- **THEN** the workflow builds x86_64 and aarch64 Linux binaries with live capture embedded, and publishes release artifacts

### Requirement: Artifact format and checksums

Release artifacts SHALL be versioned and target-qualified archives named `chronicle-<version>-<target>.tar.gz` containing the `chronicle` binary and license, accompanied by a `SHA256SUMS` file over the archives. Artifact verification SHALL be documented in the README installation section.

#### Scenario: Archive and checksum generation

- **WHEN** the release workflow completes
- **THEN** each target produces its versioned tar.gz archive plus a checksums file whose hashes match the archives

### Requirement: Version reporting

`chronicle --version` SHALL report the workspace version without introducing a new public subcommand or changing existing command behavior.

#### Scenario: Version flag

- **WHEN** a user runs `chronicle --version`
- **THEN** the command exits 0 and prints `chronicle <workspace-version>`

### Requirement: eBPF object provenance

The tracked fallback eBPF object used by no-nightly contributor builds SHALL match a fresh build from `ebpf/` source; CI SHALL detect drift. Release builds SHALL embed the object built from source.

#### Scenario: Object drift detection

- **WHEN** the tracked fallback object differs from a fresh build of `ebpf/` source
- **THEN** CI fails and the documentation states the regeneration command

### Requirement: Release artifact validation

The release workflow SHALL validate artifacts before publishing: `chronicle --version` and `--help` on the release binary, `chronicle doctor` asserting the embedded capture object probe, and checksum verification against archive contents. Artifacts SHALL fail closed if any check fails.

#### Scenario: Release binary health

- **WHEN** the release workflow validates an artifact
- **THEN** version/help/embedded-object checks pass and checksums verify, otherwise the artifact is not published

### Requirement: Distribution non-goals

The release scope SHALL NOT introduce package managers, Docker images, Homebrew formulae, or crates.io publishing; the workspace `publish = false` SHALL remain. Docker and Kubernetes packaging remain future follow-up only.

#### Scenario: No extra channels

- **WHEN** the release scope is reviewed
- **THEN** only raw GitHub Release archives and checksums are produced

### Requirement: Single deterministic checksum manifest

Each release SHALL publish one `SHA256SUMS` file covering every target archive of that release, so any consumer can deterministically find the checksum line for a specific asset. The release workflow SHALL compose this combined manifest after all target archives are built and SHALL publish it with the release (replacing any per-job partial manifest). Asset naming, archive layout, and archive contents SHALL remain unchanged.

#### Scenario: Combined manifest over all targets

- **WHEN** a release is published
- **THEN** its `SHA256SUMS` contains a verified line for both `chronicle-<version>-x86_64-unknown-linux-gnu.tar.gz` and `chronicle-<version>-aarch64-unknown-linux-gnu.tar.gz`

#### Scenario: Installer consumes the manifest

- **WHEN** the shell installer looks up its asset in the release `SHA256SUMS`
- **THEN** the line for that asset is present and verifies, regardless of which target was built first

### Requirement: Pi-generated release notes

The release body SHALL be generated by the Pi coding agent from a repository-managed prompt file (`.github/prompts/release-notes.md`) and used verbatim as the GitHub Release body. The prompt SHALL instruct the agent to inspect the checked-out repository and git history itself (current release tag or, for a tag-less dry run, the workspace version from the root `Cargo.toml`; previous semantic-version release tag or initial-public-release handling; shipped vs planned functionality; user-facing focus; exact section structure), SHALL be Markdown-only, and SHALL NOT contain GitHub Actions expressions or precomputed commit lists. Release-note generation SHALL run as a dedicated job after the release build prerequisites succeed, using `shaftoe/pi-coding-agent-action` pinned to an immutable stable release, a custom `opencode-go` provider in `~/.pi/agent/models.json` (OpenAI-compatible Chat Completions API), and the workflow-level `OPENCODE_GO_BASE_URL`/`RELEASE_NOTES_MODEL`/`RELEASE_NOTES_THINKING_LEVEL` values. The OpenCode Go API key SHALL come exclusively from the `OPENCODE_GO_API_KEY` Actions secret, referenced by environment-variable name in the provider configuration and injected only into steps that require provider access. Release-note generation SHALL fail closed: any Pi or OpenCode Go failure SHALL fail the pipeline and SHALL NOT fall back to GitHub auto-generated notes. The dry-run path SHALL reuse the same prompt file and generation job; it SHALL NOT inline the prompt or materially fork the production path.

#### Scenario: Tagged release gets Pi-written notes

- **WHEN** a `v*` tag push reaches the release-notes job with a successful build prerequisite
- **THEN** the agent receives the full prompt file contents, runs against the full-history checkout, and its response is saved to `release-notes.md` and uploaded as an artifact for the preparation job
- **AND THEN** the release is created with `--notes-file release-notes.md --verify-tag` and never with `--generate-notes`

#### Scenario: Pi generation fails closed

- **WHEN** the Pi action, the OpenCode Go provider, or the release-notes job fails
- **THEN** the publication job is skipped and the workflow run fails; no release body falls back to auto-generated notes

#### Scenario: Dry run generates the same notes

- **WHEN** a `workflow_dispatch` run reaches the release-notes job
- **THEN** the same prompt file and Pi action generate `release-notes.md` for the intended version, and a tag-less checkout is handled by the prompt itself without pretending a Git tag exists

### Requirement: Release version context validation

The release workflow SHALL resolve the release context (mode, version, intended tag) from the root `Cargo.toml` workspace version (derived, never hardcoded) via a testable script. For a real tag-triggered release, the pushed Git tag SHALL equal `v<workspace-version>` (leading `v` normalized) or the pipeline SHALL fail before any build or note generation. For a `workflow_dispatch` dry run, no Git tag is required: the intended release version is the workspace version and the intended tag is `v<version>`; a malformed or missing workspace version SHALL fail.

#### Scenario: Matching tag

- **WHEN** the pushed tag is `v0.1.0` and the workspace version in `Cargo.toml` is `0.1.0`
- **THEN** context resolution passes and the release pipeline proceeds

#### Scenario: Mismatched tag

- **WHEN** the pushed tag is `v0.1.1` and the workspace version in `Cargo.toml` is `0.1.0`
- **THEN** context resolution fails with a diagnostic naming both values and the pipeline stops before publication

#### Scenario: Dry-run version context

- **WHEN** a `workflow_dispatch` run resolves context with workspace version `0.1.0` and no Git tag
- **THEN** the intended release version is `0.1.0` and the intended tag is `v0.1.0`, no tag is created, and a malformed version fails the run

### Requirement: Release dry-run mode

The release workflow SHALL support a manual `workflow_dispatch` trigger that executes the real release preparation path as a dry run. A dry run SHALL exercise the same jobs and scripts as a real release: context resolution, eBPF build, Chronicle CLI build, per-target packaging (x86_64 and aarch64), binary validation, release-note generation with Pi/OpenCode Go, archive collection, `SHA256SUMS` generation and verification, and release-notes collection into a prepared bundle. A dry run SHALL NOT create or modify a GitHub Release, upload release assets, or create/push a Git tag, and SHALL NOT delete or mutate release-related GitHub state. Publication and any other release-mutating `gh` commands SHALL be gated to the real-release boundary: `github.event_name == 'push'` AND `startsWith(github.ref, 'refs/tags/v')`; a `workflow_dispatch` run can never reach `gh release create`. The prepared bundle (archives, `SHA256SUMS`, `release-notes.md`) SHALL be uploaded as a `prepared-release` artifact for inspection. A dry run SHALL fail on any meaningful preparation failure (build, packaging, Pi/OpenCode Go, missing notes, missing expected archive, checksum generation/verification, malformed version) and SHALL emit a job summary stating the mode, resolved version, intended tag, generated archives, notes/checksum status, and whether publication was skipped.

#### Scenario: Manual dry run completes without publication

- **WHEN** a maintainer triggers `workflow_dispatch`
- **THEN** the full preparation path runs, the `prepared-release` artifact contains the expected archives plus `SHA256SUMS` and `release-notes.md`, the run summary reports a successful dry run, and no GitHub Release, tag, or release state is created or modified

#### Scenario: Dry run cannot publish

- **WHEN** a `workflow_dispatch` run reaches the end of preparation
- **THEN** the publish job (gated to tag push) is skipped and no `gh release create` or other release-mutating command executes

### Requirement: Explicit GitHub CLI context and least privilege

Every job that invokes the GitHub CLI SHALL declare explicit authentication and repository context (`GH_TOKEN` and `GH_REPO`). Only the publication job SHALL receive `contents: write`; jobs that build, generate notes, prepare artifacts, or verify checksums SHALL remain read-only, including during dry runs.

#### Scenario: gh invocations are authenticated explicitly

- **WHEN** a release job runs any `gh release` command
- **THEN** that job declares `GH_TOKEN` and `GH_REPO`, and only the publication job holds write permission

### Requirement: Checksum completion gate

The release workflow SHALL generate one deterministic `SHA256SUMS` over all target archives and verify it (`sha256sum -c`) in the release-preparation stage, before publication. The real release SHALL NOT be created until all expected archives exist, `SHA256SUMS` exists and verifies, and `release-notes.md` exists. Publication SHALL attach `SHA256SUMS` to the release at creation and SHALL assert the release carries the `SHA256SUMS` asset afterward; a release SHALL NOT be considered successfully completed without it.

#### Scenario: Checksums generated and verified before publication

- **WHEN** the preparation stage runs
- **THEN** `SHA256SUMS` is composed from the collected archives and verified before the publish job can run

#### Scenario: Checksums missing or failing

- **WHEN** checksum composition, verification, or the post-creation asset assertion fails
- **THEN** the workflow run fails and the release pipeline is not considered successfully completed

### Requirement: Third-party release actions use immutable commit references

The release workflow SHALL reference the third-party `shaftoe/pi-coding-agent-action` at the verified full 40-character commit SHA corresponding to the intended stable `v2.27.0` release. A semantic-version tag, branch, abbreviated SHA, or other moving reference SHALL fail workflow validation. The action step SHALL retain least privilege and receive `OPENCODE_GO_API_KEY` only where release-note generation requires it.

#### Scenario: Verified action pin

- **WHEN** the release workflow is checked before publication
- **THEN** the Pi action reference is a full commit SHA and resolves to the intended `v2.27.0` release commit

#### Scenario: Version tag is rejected

- **WHEN** a maintainer changes the Pi action reference to `v2.27.0`, `v2`, a branch, or an abbreviated SHA
- **THEN** the release workflow validation fails before release publication
